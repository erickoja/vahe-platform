# Workshop Pilot audit, 3 Oct 2026

Method: full read of the billing/webhook/email/calendar/metal/notify edge functions, all SQL (RLS, invites, proposals), the billing + gating code in App.jsx, a lint + production build, HTTP checks of the live marketing and app hosts, and a read of the landing/terms/privacy copy against the app.
Not done: no live clicking through the app, no real signup, no Stripe checkout (the in-app browser was refused for the marketing site, and signup/payment steps are off limits to me). Nothing was changed in any live database or Stripe account.

Status key: FIXED = changed in the working tree (not committed or deployed). NEEDS YOU = action only you can take.

## Critical / High

| # | Issue | Impact | Status |
|---|---|---|---|
| 1 | **Owners can edit their own billing status.** `st_update` RLS lets a studio owner/admin UPDATE their `studios` row, and RLS is row level, not column level. Via the REST API with their own token they can set `sub_status='active'`, `trial_ends_at='2099-…'`, etc. | Free use forever, or wiping their Stripe link. Revenue leak. | FIXED in code: `supabase/billing-protect.sql` (trigger blocks billing-column changes by logged-in users; service role and SQL editor still work). **NEEDS YOU: run it on the customer project `ietkgxvmxzeqjhxmdddx`.** Verify: PATCH `sub_status` with a user token must fail, renaming the studio must still work. |
| 2 | **`send-email` is an open relay.** "Verify JWT" accepts the public anon key (it is a valid JWT and ships in the app bundle). The function itself checked nothing. | Anyone can send arbitrary HTML email to anyone from your sending domain (spam/phishing, domain blacklisting, Resend account suspension). | FIXED in code: now requires a real signed-in user, validates addresses, size caps. **NEEDS YOU: redeploy `send-email`.** |
| 3 | **Past-due customers get a Subscribe button, not "Manage billing".** After a failed renewal the card showed Subscribe monthly/annual and no portal button. | Customer re-subscribes and is double billed, and the old past-due sub later cancels. | FIXED in App.jsx (past-due shows "Update payment method" + warning, no Subscribe). |
| 4 | **Stale subscription cancels a live one (webhook).** `customer.subscription.deleted` / `invoice.payment_failed` marked the studio canceled/past_due regardless of which subscription the event was for. | A studio that replaced an old past-due sub with a new one would be flipped to canceled when the old one expired, while still paying. | FIXED: webhook ignores events for a subscription that is no longer the studio's current one. **NEEDS YOU: redeploy `stripe-webhook`.** |
| 5 | **Checkout could create a second live subscription** (billing fn never checked for an existing one). | Double billing via double click, second tab, or direct call. | FIXED: billing fn returns 409 when the studio already has an active/past-due sub. **Redeploy `billing`.** |

## Low / info

- **Cancel-at-period-end is invisible.** If someone cancels in the portal, status stays Active until the period ends and the card gives no hint. Recommend storing `cancel_at_period_end` and showing "Ends on <date>".
- **Upgrade/downgrade (monthly↔annual)** only exist through the Stripe portal. The code cannot confirm the portal is configured to allow plan switching, check Stripe → Settings → Billing → Customer portal → "Customers can switch plans".
- **Unlimited free trials**: every new email gets 14 days; already tracked as "signup abuse controls".
- **`metal-prices` unit heuristic** (`gold > 1500` ⇒ divide by troy-oz) would wrongly convert currencies where a gram of gold legitimately costs more than 1500 (JPY, KRW, INR). Harmless for AU/NZ/UK/IE, wrong if you add those regions.
- **Landing page had 11 `<h1>` tags** (10 came from the product mockups). FIXED (mockup headings are now `div`s), one real H1 remains. Good for SEO/accessibility.
- `printProposalDoc` is dead code with a stub body and an undefined `esc` (never called).
- Lint: 91 unused vars, 35 empty catch blocks, 4 unreachable blocks, 6 impure-render warnings. No functional impact found beyond items above.
- Terms say you can cancel "from your account", true only via Manage billing (active subs). Account deletion/closure has no in-app button (Terms/Privacy say you can ask), so it is by email only.
- `FAQ: "Each studio's data is isolated"`: `public-proposals-rls.sql` (per-studio proposal RLS) is still in the "run on prod" backlog. Until it runs on both projects, any logged-in user of one studio can read/write other studios' *proposals* table rows. Confirm it has been run on `ietkgxvmxzeqjhxmdddx`.
